# 货架表格导入

导入只创建待确认变更集。确认、修订检查、逐项修正、暂缓和单事务写入沿用[货架变更集](product-shelf-changesets.md)。上传的工作簿不成为资料文件，也不保留客户原件。

## 网页导入

开启货架的库在资料页提供“导入”页签。选择或拖入一个工作簿，指定已确认方案及可选的文件生效日期，然后“按此方案试导入”；返回的原有或新批次直接打开待确认页，不自动写入货架。

首次方案可以手工配置，也可选择文件并显式请求本库模型建议。网页分别维护产品地图、认证进度、证书报告、海外核对和资料要求的方案，不把不同文件种类混成一份方案。可编辑工作表、表头行数、产品线、列映射、型号拆分、占位值、状态与颜色含义，以及各文件种类需要的配置。未保存的映射阻止试导入，避免使用旧方案。模型建议须明确核对不确定项后再保存。保存方案通过单操作变更集确认，修订冲突或失败保留编辑内容。

导入历史按每页 20 个批次读取，包含已确认和待确认批次；生效时间明确显示 UTC，录入日历日期按 UTC 零点提交。网页上的文件选择只暂存于当前页面，失败时保留以便修正日期后重试。

## 导入方案

`GET /libraries/:id/shelf/import-plans` 返回当前库的方案，按 `key` 排序。每个文件种类用一个稳定的方案键。读取方案附带该方案最新批次的 `last_file_name`，尚无批次时省略。支持 `product_map`、`certification_progress`、`certification_report`、`overseas_sales` 和 `atq`。DC 与 AC 证书汇总都使用 `certification_report`，各工作表分别配置。

方案也通过变更集保存，没有直接修改货架的旁路：

```json
{
  "source": {"type": "web"},
  "operations": [{
    "id": "map_plan",
    "type": "save_import_plan",
    "import_plan": {
      "key": "product_map",
      "name": "产品地图",
      "file_kind": "product_map",
      "revision": 0,
      "sheets": [{
        "worksheet": "Map",
        "product_line_id": "existing-line-id",
        "header_rows": 2,
        "columns": [
          {"column": "A", "field": "platform"},
          {"column": "B", "field": "product"},
          {"column": "C", "field": "model"},
          {"column": "D", "field": "sale_status", "key": "configured-region"},
          {"column": "E", "field": "parameter", "key": "configured-energy"},
          {"column": "F", "field": "description"}
        ]
      }],
      "model_separators": [";", "\n"],
      "missing_values": ["待定", "型号待定", "TBD"],
      "status_values": {"GA (Demo)": {"status": "GA", "notes": "Demo"}},
      "fill_meanings": {"FFFFFF00": "uncertain"}
    }
  }]
}
```

产品线、区域及参数定义先在本库确认。每张工作表分别指定表头行数；列用 Excel 字母定位，不依赖表头文案。平台、产品名称和型号列必填。参数仅接受归属该产品线的活动文本、数字、布尔、日期或单选字段。未知工作表必须显式映射或设 `ignore: true`。未映射的列忽略。

首次保存的修订号为 1；更新须提交当前 `revision`。读取结果的方案内容在 `definition` 内，写入时使用上例的平铺字段。方案的工作表、拆分规则、占位值、状态写法与颜色含义都由提交方确认，不包含客户默认配置。首次方案可以显式请求模型建议，见下文。

`model_separators` 按列出的顺序拆分型号，不修剪或改写拆分后的名称。`missing_values` 明确列出不能视为型号等身份字段的占位写法。数值参数支持数字及 `9~54`、`9～54` 形式的闭区间；布尔接受 `true/false/1/0`；日期接受 `YYYY-MM-DD`。

`status_values` 将确切原文映射为固定状态及备注，仍保存原始状态文字。空白写法不能配置默认状态，须逐行决定。填充色使用大写 ARGB，如 `FFFFFF00`；索引色使用 `indexed:13`，主题色使用 `theme:4:0.5`，无 tint 时末尾为空。颜色含义可为 `ignore`、`uncertain`、`planned_eom` 或固定状态。固定状态颜色只核对区域文字，不替空白区域填写状态。身份或描述列的 `planned_eom` 作用于该行区域，区域列的标记只作用于该区域。未知颜色、无法确定含义的颜色和文字矛盾都成为待确认冲突。

## 首次方案的模型建议

`POST /libraries/:id/shelf/import-plans/suggest` 接受 multipart 的 `file`、`plan_key` 和 `file_kind`。支持的文件种类与普通方案一致。已有该方案键时返回 `409`，后续修改继续使用已有方案的修订号。该请求不要求文件日期，因为它只提议配置，不导入业务事实。

模型使用本库配置的 generation 处理模型，不借用其他库。未配置时返回 `400`。输入包含每张表前 20 个有数据行、总行数、单元格原文、颜色、合并范围、公式标记，以及本库产品线、部件身份和字段、模块、区域、阶段、标准配置。公式不执行，解析器认证信息等其他设置不发送。序列化输入或输出超过 256 KiB 时拒绝，提示缩小文件或手工配置。

返回 `201` 和普通待确认变更集，其中包含一个 `save_import_plan` 操作。建议的 `import_plan` 可编辑，`issues` 中的 `uncertain` 保留待核对的含义。方案键、文件种类和初始修订号由服务端固定，模型不能覆盖。请求不保存当前方案，也不试导入数据。

审核者检查工作表、产品线、字段、拆分及颜色含义后，通过 `replace` 决定提交修正后的完整操作，移除已经解决的 `issues`，再确认变更集。普通 `apply` 不会跳过这些冲突。保存仍检查配置与修订号；审核期间其他人先保存同键方案时，旧建议不能覆盖。拒绝或暂缓沿用变更集的 `discard`、`defer` 决定。

模型失败、无效 JSON、截断或内容过滤结果不会留下建议批次，不会改动当前方案。普通上传始终使用已确认方案确定性解析，不自动调用模型。

## 自由文本的拆分建议

`POST /libraries/:id/shelf/imports/suggest-text` 使用 JSON。`text` 原样保留，最多 20,000 字节。`source` 可省略，默认为网页；来自导入的请求应携带原批次来源及文件日期。`import_location` 可传工作表和单元格；返回操作的 `import_location.values.source_text` 保留原文，审核后仍可追溯。生效时间沿用导入来源或操作指定的 `effective_at`，不接受未来时间。

描述转参数时，提交明确的型号 ID、当前修订号和操作类型。模型只建议该型号所属产品线的活动字段，支持数值及范围和部件条件：

```json
{
  "kind": "parameters",
  "text": "能量 9~54 kWh",
  "operation": {
    "type": "set_parameter_values",
    "entity_id": "existing-model-id",
    "revision": 3
  },
  "import_location": {"worksheet": "Map", "cells": ["F3"]}
}
```

样品描述转部件条件时，`kind` 为 `conditions`，`operation` 提供完整的 `create_certification` 或 `update_certification` 提议。型号、所属节点、标准、地区、名称及其他元数据由提交方指定，模型只填写 `certification.conditions`。候选部件来自所属节点在生效时点覆盖的型号组成，不按近似名称新增部件或改变认证身份。认证进度与证书汇总方案可以映射 `sample_description` 列；非空样品描述会保留原文并阻止该认证提议直接确认，随后可显式请求条件建议。

多型号单元格用 `kind: "models"`、`text` 和 `parent_id`，后者必须是本库已有的活动产品名称节点，不传 `operation`。模型返回的原始名称分别形成 `create_entity` 和 `save_relation` 提议，层级由服务端固定。名称保留空格和标点；不能确定的缩写、斜杠或共享前缀不自动补全。已有同名身份继续使用原有人工确认规则。

三类请求都返回待确认变更集，每项带 `uncertain`，无法按原文拆出的名称带 `unparseable`。空结果也保留原文与冲突。审核者使用 `replace` 提交检查后的完整操作并移除已解决的 `issues`，然后确认。参数类型、部件所属、认证识别键、同名身份及修订号仍由同一变更集校验。模型输出不能绕过这些校验。

拆分请求返回独立待确认变更集，不修改原导入批次。针对原批次的同一项，应明确放弃原提议或保留其待处理状态，避免重复确认。参数目标、认证所属节点和拆分型号的父节点须先有明确身份；尚未建立的层级先按原导入确认。新界面可直接使用这两个建议接口和现有变更集审核接口。

## 上传与确认

`POST /libraries/:id/shelf/imports` 使用 multipart：

| 字段 | 含义 |
| --- | --- |
| `file` | `.xlsx` 工作簿 |
| `plan_key` | 已确认方案的键 |
| `file_date` | 可选 RFC3339 生效时间；取不到可靠文件日期时必填 |

文件名中恰好有一个有效日期时，识别 `YYYYMMDD` 或用 `-`、`.`、`_`、`年/月/日` 分隔的两位月日，按 UTC 零点生效。没有日期、日期异常或多个日期时要求填写，不使用上传时间或 Office 的编辑时间。显式日期优先，零时间和未来时间拒绝。

返回 `201` 与普通待确认变更集。同一库、文件内容、方案键及修订、生效时间确定一个批次；重复上传返回该批次及已保存的处理进度。文件重命名不改变内容身份；返回来源保留首次上传的文件名。上传不自动确认。

导入沿用名称、别名和代码的确定匹配，不做模糊身份推断。合并单元格只展开明确的合并范围，不向空白行填充前一行；两行或多行表头按方案跳过。同一型号重复行、跨平台同名产品、分组标题、空区域、未知状态、公式和无法解析的参数交给提交方处理。必填缺失行不生成层级或型号；区域空白可修正相应属性提议为无记录，或明确填写状态。

已有属性以文件日期的快照为基础，只提议映射字段；未映射字段及后续快照继续沿用属性时间线规则。手工值与导入提议不同时，变更集展示原值并等待明确决定。不同类别同名仍须确认。

上一已确认文件的活动型号在新文件中消失时，生成 `missing_entity`，由提交方选择保留或退市，不删除实体。同一导入批次的已确认部分和后来确认的暂缓部分合并比较。首次导入不把库中其他型号视为消失。

来源包含 `import_batch_id`、`import_plan_key`、`plan_revision`、`file_name`、`file_sha256`、`file_date`；每项的 `import_location` 保存工作表和单元格，确认日志也带相同位置。方案、批次、决定和来源随维护副本导出恢复。迁移 49 新增方案表，存在方案或导入批次时拒绝开发降级。

## 认证进度与证书报告

认证工作表指定 `owner_kind`（`model`、`part`、`product` 或 `platform`），用 `owner` 列按名称、代码、明确别名或 ID 确定所属节点。可选 `product_line_id` 限定所属范围，按文件日期检查层级；无法证明属于指定产品线时转人工。共同必填列为 `owner`、`standard`、`certification_object` 和 `region`。地区单元格允许明确为空，仍参与识别。标准只按本库已配置的键、规范名或别名解析，不从名称猜年份。

其他列可映射 `name`、`year`、`cell_part`、`agency`、`progress`、`start_date`、`obtained_date`、`issued_date`、`validity`、`number`、`cloud_url` 和 `sample_description`。名称与文字原样保存。已有认证只更新映射列，未映射字段和适用条件保留。识别键仍为所属节点、标准、认证对象、电芯部件和地区；零条匹配产生人工处理冲突，须明确改为 `create_certification` 并填写原始名称；多条匹配须提交含完整记录及目标修订号的修正操作，避免遗漏候选中的其他字段。同键重复行须逐项处理，不自动合并。`model_separators` 也用于拆分型号类别的所属节点列，不修剪拆分后的名字。

证书汇总工作表另需填写 `progress`，明确本表表示已完成认证的原文。若同时映射进度列，其值须与该配置一致。汇总可增加 `pack_model`、`cluster_model`、`container_model` 和 `model` 列。电芯部件不存在时提议新增，存在时提议更新属性，均须有已配置的工作表 `module_type`。Pack、簇和集装箱型号只成为部件属性。`model` 对应明确的型号或 AC 表项目名称，用于提议组成；所属节点本身是型号时可省略这一列。`model` 列也按已确认的 `model_separators` 拆分。多个型号合用同一部件时复用该部件，不生成副本。已有不同模块或重复行中不同的部件属性交给提交方处理。

认证日期接受 `YYYY-MM-DD`、`YYYY/M/D`、`YYYY.M.D`、`YYYY年M月D日`。Excel 内置日期格式 14 至 17、22 的整数日期序号按工作簿 1900 或 1904 日期系统转换。虚构的 1900 年闰日、分数日期、异常日期及无法判断的自定义显示格式成为 `unparseable`，保留原单元格，不补日期。有效期保留原写法。新批次的 `import_location.values` 保存映射单元格原文，公式另存 `.formula`。

## 海外清单交叉核对

海外工作表使用 `overseas_sales` 和明确的 `owner_kind`。`owner` 必填，至少提供一类状态或认证核对列。`sale_status` 列的 `key` 为区域配置键，沿用 `status_values` 解释原文。核对覆盖文件日期的货架记录；多种选配状态不能当成一条统一状态。

认证的 √/× 矩阵用 `field=certification`，`key` 指定规范标准键。工作表的 `check_values` 明确符号含义，例如 `{"√":true,"×":false}`；工作表 `progress` 明确表示完成认证的原文。核对复用节点读取中的部件、上层和适用条件语义；只覆盖部分选配时保留提示。未知符号或身份不明确仍须由提交方修正。

也可映射 `standard` 列，配合 `certification_object`、`cell_part` 和 `region` 限定直接所属认证，再核对 `progress`、`agency`、`validity`、`number`、`cloud_url`。认证零条或多条都只报告双方证据。核对结果保存为 `import_notice` 操作，差异类型为 `cross_table_contradiction`，详情含货架值与表格值。确认提示不会创建或修改实体、属性、关系或认证，数据一致的行也保留无冲突的核对项。

## ATQ 资料要求

ATQ 工作表用 `atq`，明确指定一个 `product_line_id` 或 `module_type`，绑定到产品线或配置模块。名称列可以是 `name`、`name_zh` 或 `name_en`；按这个顺序选第一个已映射的列作为实体名称，所选单元格空白时不改用另一列。`name_zh` 与 `name_en` 同时作为中英文元数据保留。所属清单自动保存为 `requirement.list_name = 方案键 / 工作表名`，保留工作表原名；名称、代码和已有明确别名只在该所属清单内匹配，不做相似合并。不同工作表或不同方案中的同名要求独立，同一工作表的重复名称仍交给提交方处理。

`due_stages` 必填，映射原表“研发最迟提供时间”。原表阶段列另映射 `stage_label`，只展示。单个配置阶段名或键表示终稿应交阶段；两项可以写为 `初稿：阶段名；终稿：阶段名` 或 `阶段名（初稿）；阶段名（终稿）`，也支持半角标点和换行。阶段名来自本库配置。无法确定的自由文字须人工确认；可在方案的 `deadlines` 中按完整原文指定 `draft_stage` 与 `final_stage`，例如：

```json
{"deadlines":{"提交方确认的原文":{"draft_stage":"configured_draft","final_stage":"configured_final"}}}
```

原始期限另存 `requirement.due_text`。不根据 `stage_label` 补到期阶段，不根据上传时间生成清单版本。其他列为 `file_category`、`owner`、`priority`、`source_list`、`source_version`；`market` 列的 `key` 为区域键，值接受 `required/optional/not_needed` 或 `必需/可选/不需要`，其他写法须修正。未映射元数据保留，映射的空值明确清空。

新版只在相同所属清单内匹配已有要求，新增要求进入新增提议，旧要求更新保留身份。同名要求在另一张工作表出现不表示本清单仍有该项。以前确认过的活动要求若在其所属清单的新版消失，生成 `missing_entity`，明确选择 `retire` 后归档；不会自动归档或删除文件，所有型号沿用当前活动清单。被忽略、缺失或包含未解析行的工作表不据此推断消失，须先修正后重新导入。放弃异常行、稍后确认暂缓部分或保留旧项，不会使先前活动要求失去后续版本的消失追踪。


所属清单与 `source_list`、`source_version` 分开保存。后两者是可选的来源原文与版本列，不参与身份匹配。修改方案显示名或清单版本不改变身份；修改方案键或工作表名会形成新清单，系统不会猜测是否改名。迁移前没有所属清单的要求保留在“历史未分清单”，需提交方核对归属后通过变更集维护；新导入不会仅因同名而改写这些历史要求。一份资料文件可用 `requirement_ids` 同时关联多个清单中的要求，型号清单仍分别计算各项状态。详情见 [变更集契约](product-shelf-changesets.md)。


## 文件边界

单文件及 ZIP 解压后的总量最多 32 MiB；最多 2,000 个 ZIP 项，每张表最多 10,000 行、100,000 单元格和 10,000 个合并范围。批次沿用 500 操作上限，超过时拒绝并要求拆分工作簿。原件只暂存于请求解析阶段，结束后清理。

只读取数据型 `.xlsx`，不执行公式或访问外部引用。除上述内置日期外，自定义数字显示格式、条件格式等不能确定含义的内容须先提供明确值；不通过推测补全型号或自由文本参数。测试在代码中构造脱敏片段，客户原件不进入仓库。
