# 0029 推荐容器中的本地 Pi 作为 Agent 入口

Status: accepted
日期：2026-11-17

## 背景

客户曾用通用客户端（自报 Codex）持完整 API Key 直连 MCP 写入产品货架。客户端自行拆分清单、写入未定义字段，把计划取证日期写成实际取证日期，猜测型号对应、跳过行并自行确认全部变更集。通用客户端能执行命令和改写文件，Reliquary 无法约束其行为，仅靠使用规则不能保证按导入流程操作。

## 决策

推荐本地 Pi，在 Docker 容器中运行，宿主机沿用 Python 和 Docker，无需另装 Node。只读挂载一个工作文件夹，默认是运行根目录的 `workspace/`，容器内为 `/workspace`；Pi 自身配置、凭据与会话另挂载到 `/data`。工具白名单为内置 `read`、仅连接 Reliquary 的 MCP 工具，以及项目的 `reliquary_upload_workbook`、`reliquary_stage_attachment`，不开放 bash、edit、write。

表格导入必须走导入方案：已有已确认的 `plan_key` 时上传生成待确认变更集；没有方案时用 `new_plan_key` 与 `file_kind` 请求待审核方案建议，不自行拆表或逐行手写业务事实。原件暂存取得附件 ID 后，再通过 MCP 提议归类。上传、暂存和建议不确认货架变更，差异须经用户审核确认。

本体安装成功后显示数据外流说明，默认询问是否配置 Pi；允许跳过，非交互或跳过时打印后续命令。通用客户端仍可接入，飞书仍是可选入口。沿用 [ADR 0028](0028-optional-feishu-entry.md) 的口径，启用前须说明并取得客户同意：每轮完整上下文（问题、工具读到的资料片段、工作文件夹中读到的内容、历史回复）发送给所选模型服务商，ChatGPT 订阅经 Reliquary 后端转发给 OpenAI；资料库正文、文件和数据库不整体同步出去。

## 取舍与验证

被否决的方案：只认 Pi 入口，需要给 API Key 分权限并限制其他客户端，客户也会失去自选工具的自由，暂不做；在宿主机通过 npm 安装，要求客户另装 Node，且 Pi 能访问用户全部文件；保留完整编码工具，bash、edit、write 正是这次问题的来源。

代价与限制：模型仍能通过 read 读到容器内 Pi 自己的凭据文件；对话上下文进入模型服务商的留存范围。本地 Pi 会话暂未纳入 `reliquary-admin` 备份，与飞书状态备份分开。工具白名单不等于服务端权限隔离：API Key 仍无权限范围，本机调用方仍可沿用 [ADR 0015](0015-no-login-local-only.md) 通过免 Key 的回环 HTTP 接口绕过入口限制。

验证：`pi-configure` 生成受限工具配置、技能包副本和 `scripts/pi`，实际要求模型成功调用 `list_libraries`；`pi-update` 重建镜像、刷新规则与技能并做同样检查。启动器只读挂载工作文件夹，`scripts/pi -c` 继续上次会话。上传扩展只接收工作文件夹内的普通文件，不确认货架变更。
