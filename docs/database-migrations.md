# 数据库迁移规范

任务 15 起，`migrations/versioned/000000_init.up.sql` 和 `000000_init.down.sql` 是冻结基线。它们对应任务 14 的提交 `a27386002421eb95857eb5988f53894e8a9d1cd0`。已安装的数据库从基线之后逐个升级；不能通过修改基线给已有数据库补结构。

结构变更必须新增一对迁移，从 `000001` 开始按序编号，例如 `000001_maintenance.up.sql` 与 `000001_maintenance.down.sql`。提交前检查编号没有重复，检查新增表、列是否已加入维护数据归属清单。列未归类时，维护测试必须失败。

每次结构变更要有真实 PostgreSQL 测试：用上一版本的结构写入代表性数据，执行新增迁移，逐表比较升级前后的不可再生字段及行数。改列时先转换和验证原数据，验证失败则回滚迁移，不能通过删行满足新约束。另在临时数据库执行全部 up、全部 down、全部 up，结束后删除临时库。

显式升级使用 `./reliquary-admin upgrade`。命令默认不备份；准备镜像后暂停收录并停止应用，再执行历史资料导出、必要迁移和当前数据一致性核验。默认路径不生成升级前全量清单，也不做升级前后全库摘要比对；迁移的数据保全要求由上述真实 PostgreSQL 测试验证。失败后不解除维护暂停，不强制标记迁移成功，也不自动清空数据库。

需要本次升级前的完整恢复点时，明确使用 `./reliquary-admin upgrade --backup`。该模式先创建并校验包含旧代码、旧镜像与数据的完整备份，再迁移并按备份清单核对。备份与部署解耦；独立定时备份不因升级而改变。

生产不支持数据库结构降级。退回旧版本需要已有的完整备份，将旧代码、旧镜像、旧数据库、文件库和上传资源整体恢复到新的空目录和空数据库；核对通过及必要凭据重新填写后再使用。没有本次升级前备份时，不能保证恢复到此次升级前的最新状态。`down` 文件只用于开发测试和临时环境验证，不能作为生产退回办法。恢复旧快照不会包含该快照之后的新数据。

备份不包含密钥和可用令牌，恢复会生成新的系统加密密钥、JWT 密钥和数据库密码。模型 API Key、ChatGPT 登录、收录 API Key 等要重新配置。账号密码哈希可以保留，原账号仍可以登录。详见 [个人使用指南](personal-use.md) 和 [维护数据归属](maintenance-data.md)。

## 删除采集表的导出步骤

`000005_remove_collection` 删除 `data_sources` 与 `sync_logs`，历史文章的 `channel`、来源 metadata 与转载来源保留。`reliquary-admin upgrade` 无论是否选择备份，都在执行该迁移之前运行 `export-sources`，将无密钥的数据源配置与同步日志写入文件库 `.reliquary/exports/`。导出失败时迁移不执行，收录保持暂停；旧备份恢复也遵循相同步骤。

开发环境直接执行 SQL 或迁移工具之前，先使用相同数据库与文件库配置运行：

```bash
./reliquary-admin export-sources
# 随后才执行开发迁移工具
```

单独导出不会恢复采集功能，不会删除数据。版本 4 到版本 5 的测试须同时核对导出内容、其余表全部不可再生字段及行数；全部 up、down、up 仅在临时数据库验证。

## 库命名迁移

`000007_library_naming` 将资料集合改称 Library：`knowledge_bases` 改为 `libraries`，六张表的 `knowledge_base_id` 改为 `library_id`，同步改名索引和约束，并按原参数重建两个保存列名的 BM25 索引。运行行为及单库约束不变。

本次保留 `000000` 至 `000006`，因为离线维护在同一事务中读取 `000002`、`000003` 的 up/down SQL，恢复历史结构的备份；采集配置导出和列归属核对也依赖版本 0 至 5 的含义。合并并重用版本 0 会使这些已有恢复能力无法区分新旧结构。新安装执行完整迁移链至版本 27。当前数据库的维护副本格式为 6，旧格式 1 至 5 仍可读取和核对。

## Redis 待处理操作迁移

`000009_redis_pending_ops` 新建 `task_pending_ops`，移除 `task_jobs` 的领取、租约和任务心跳字段。旧队列消息不导入新队列，已有死信与每日计数保留；死信的库 scope 改为 `library`。版本 000008 的 Markdown 收录迁移先执行，随后执行版本 000009。维护副本格式升为 5，版本 9 起使用待处理操作列归属，版本 9 以前的离线维护仍使用原队列表列归属。恢复后的未完成操作在后端启动时补推 Redis。

## 五库配置迁移

`000010_system_libraries` 解除空间唯一活动库限制，增加系统角色、模板、目录和可配置标准，创建内容类型及关系类型子表。原库 ID 保留并成为机构发布，历史本人文档和报告迁到对应系统库，索引外键同步。空间增加共享向量模型选择，旧库模型字段仅作兼容数据保留。库身份及资料归属增加不可变触发器。该版本迁移完成后，维护列归属按版本区分新增配置；副本格式仍为 5，没有改动已有名称或序列化格式。

## 收录契约迁移

`000011_ingest_contract` 为资料增加 `source_ref`、`source_body_hash`、`identifier` 和可空的 `graph`。前三列默认空字符串，graph 默认 NULL；旧资料内容与记录数不变。来源标识不唯一，按空间、库、来源和收录时间建立最新记录查询索引。维护列归属在版本 11 加入四列，版本 0 至 10 保持原规则；副本格式仍为 5，旧副本升级核对仅投影这四个默认值。down 仅供临时环境验证。

## 按库审核与去重迁移

`000012_library_intake` 将丢弃记录主键改为 `space_id, library_id, fingerprint`，保留原链接、资料 ID、原因和时间。仍能定位原资料的历史记录使用该资料的库；原资料已删除而无法确定原库的记录保存在 `legacy-space:<space_id>` 范围，仅留存证据，不拦截任何当前库。指纹使用 SHA-256。增加本库 `identifier` 查询索引，转载来源唯一约束显式包含库，并允许机构、标题、日期匹配方式。

维护列归属从版本 12 起加入丢弃记录的 `library_id`、`fingerprint`；副本格式保持 5，旧副本恢复和升级核对采用相同的确定性转换，所有旧列与行保留。开发 down 遇到新式正文指纹、跨库同链接或新式转载匹配等无法无损表示的数据会报错，不能通过删除记录降级。生产继续使用升级前完整备份恢复。

## 检索位置与候选向量迁移

`000014_search_positions_vectors` 为分块增加 `source_locations`，为向量重建增加候选标志、切换时间、候选向量及旧向量归档。编号 000013 曾预留给 ikb-07；该任务只改文件与副本格式，没有数据库结构变更，因此未使用。000014 的 down 只用于临时库，不作为生产恢复方式。已有分块在重处理时计算位置；新分块及补图立即计算。

新列、表在维护列归属中按版本 14 分开：位置和向量集可重算，重建运行的候选标志、切换时间属于操作状态。空间没有明确向量选择时采用本机 Qwen3-Embedding-0.6B；已有明确模型选择保留。全部旧向量在升级中保留，不自动重算或切换。副本新字段导入与旧副本默认值投影已接入维护核对。

## 主题与关注动态按库迁移

`000015_library_topics_feed` 增加 `topics.library_ids`，空数组表示全部库；增加 `follow_feed_library_states`，按空间和库保存上次查看时间。升级将原空间检查点复制到该空间每个已有库，原 `follow_feed_states` 保留用于历史副本兼容。当前新安装继续执行后续迁移至版本 27。

`library_ids` 和分库检查点属于 Sidecar，后者在 `PersistentTables` 登记为 `data/follow_feed_library_states.json`。旧版列归属不引入新列；旧副本导入与升级核对采用同一默认值和检查点复制规则。副本格式保持 5，登记格式保持 1。down 仅供开发临时库验证；生产仍从完整备份恢复。

## 长文检查点迁移

`000016_entry_segments` 新增 `entry_segment_runs`，记录每篇资料审核与处理的逻辑运行、分段计划、逐段状态和结果、合并结果。升级只新建空表，不改旧行；down 仅供临时环境验证。

全部列按版本 16 登记为维护 sidecar，依赖空间与资料。副本格式仍为 5。维护核对记录结构版本，只为旧版本补上新增表的空默认值；现有检查点被改动或丢失会核对失败。检查点随着资料删除级联清理。

## 联合处理结果迁移

`000017_processing_outputs` 删除旧的 `entries_content_type_check`，内容类型改由服务层按所属库校验。新建 `entry_processing_outputs`，每篇资料保存最近一次处理的正文哈希、内容类型、运行 ID、关系证据与图片说明，包括图片跳过原因。该表不是关系正本，没有来源计数或抑制字段，资料删除时级联清理。

全部列从版本 17 起登记为维护 sidecar，进入 `.reliquary/data/entry_processing_outputs.json`，依赖空间、库和资料。旧副本升级核对仅投影空表；当前非空结果被篡改或丢失仍会失败。副本格式仍为 5，登记格式仍为 1。当前新安装继续执行后续迁移至版本 27。开发 down 遇到旧全局类型清单不能表示的资料会拒绝，保留原行与处理结果；生产仍使用升级前完整备份恢复。

`000018_relations` 新建关系、按资料唯一的关系来源、库内抑制、关系类型合并及按实体的图谱待同步记录。升级只新建空表，保留此前处理证据与全部旧行；已保存资料在后续重新处理时发布关系正本。关系版本从 1 开始，每次联动事务递增；删除留下待同步通知，重新出现的三元组使用新关系 ID。

## 模型调用内容迁移

`000024_model_call_contents` 为调用账本增加 `processing_attempt` 与 `span_id`，旧行分别补 0 与空字符串。新表 `model_call_contents` 用相同调用 ID 外键保存 gzip 压缩的完整请求和响应、字节数、响应类型、HTTP 状态与接收完成标志。账本删除级联删除内容，资料删除触发器清理其全部调用内容，保留历史统计。两列的 `model_call_content_deletions` 保存删除标记；内容写入与资料删除使用同一事务级 advisory lock，延迟到达的异步写入不能重新创建已删除的资料内容。审核调用可能早于资料事务提交，因此内容不直接引用资料外键。

`000027_system_library_directories` 将系统角色和默认目录从 `institutional`、`opinions`、`mine`、`ai-reports` 分别改为 `official`、`media`、`personal`、`ai-output`；`references` 保持不变。库 ID、资料归属、正文、来源类型、模板与审核规则不变。系统库使用的自定义目录保留。

数据库迁移之后，服务按已迁移的归档记录搬迁文件目录，保留文件原字节；目标非空、路径为符号链接或其他目录冲突时停止，不覆盖文件。仅文件库恢复先核验原副本，再导入并搬迁目录。搬迁后首次刷新副本前，旧清单只允许按已核验的系统库目录映射读取新路径，仍验证原始 SHA-256 与文件大小。新版副本写入新路径。维护副本格式和持久表登记版本不变。

## 模型调用分模态计费

`000029_model_call_modalities` 为账本增加可空的 `text_input_tokens`、`image_input_tokens`、`image_input_price`。旧行保持 NULL，原 token、单价和费用不变。三列全部为仅备份证据，从版本 29 起登记；旧版本升级核对只允许将新增 NULL 列投影省略，非空分项及原账本仍逐行核对。副本格式保持 6。down 仅用于临时测试库，生产回退使用升级前完整备份。

## 删除旧关系与图谱，结构版本 33

`000033_remove_relations_graph` 删除关系、来源、抑制、类型合并、关系类型及图谱待同步表，清理旧图谱同步、核对及重建的待处理任务，并删除处理输出的 `relations`、内容类型的 `extract_graph` 与资料的 `graph` 字段。资料正文、来源元数据、图片、实体和其余业务数据保留。旧关系数据不迁移，开发 down 只重建空结构，不能恢复删除的数据。

维护列归属按版本核对，历史副本导入到当前结构时移除上述退役表列；其余数据继续严格核对。备份、恢复、重建与恢复演练只依赖 PostgreSQL、Redis 和存储，不再执行 Neo4j 操作。升级默认不备份，生产退回仍须使用已有完整备份。

发布版本 33 前，按本机部署文档同步运行目录的 `config/prompt_templates/processing.yaml` 与 `content_check.yaml`。输出结构与代码同时变化，运行副本不能继续保留 `article_relations` 模板或要求调用旧图谱工具；严格启动校验会拒绝已删除的模板 ID。`verification.yaml` 不再加载，无需 Neo4j 配置或服务。

## 删除内容类型、主题与资料自检

`000034_remove_classification_checks` 删除 `library_content_types`、`topics`、`entry_topics`、`topic_backfill_jobs`、`topic_backfill_batches`、`content_check_settings`、`content_check_runs`；删除资料的 `content_type`、`content_type_corrected`、`content_type_hint`，处理输出的 `content_type`，以及关注表的 `topic_id`。主题关注和 `topic:backfill`、`content:check` 待处理任务删除，实体关注保留。全文表头函数和触发器同步去掉主题，重算派生检索文本。

本迁移永久删除上述分类、自检及主题关注数据；资料正文、图片、来源、星标、实体关联和其他数据保留。开发 down 只重建空结构，不恢复已删除的数据。不备份不影响迁移执行，但不能保证恢复到此次操作前的最新状态；生产退回仍需要此前校验过的完整备份。

发布时须同步新的 `config/prompt_templates/processing.yaml`；`topic_backfill`、`content_type_hint` 不再是有效模板 ID，`content_check.yaml` 不再加载。部署与备份继续独立执行。


## 事实与事件最小链路迁移

`000039_facts_stories` 新建 `stories`、`facts` 与 `entry_facts`，保存事件首次与最近新事实时间、事实框架和发生时间、资料关联角色、逐字引文与人工标记。一篇资料最多作为一个事实的出处，由部分唯一索引约束；每个事实必须属于一个事件。发生时间以可空文本保留 `YYYY-MM-DD` 或 RFC3339 表示，避免把仅日期转换成午夜时刻；查询时间线时才生成排序用的时间值。事件首次与最近新事实时间仍为 timestamptz。升级仅增加空表与索引，不改写已有资料或目录。

三张表的全部字段从结构版本 39 起按 Sidecar 登记，并按事件、事实、资料关联的依赖顺序导入。旧副本升级只补空表，现有非空事实与出处丢失仍会核对失败。副本格式及登记格式保持不变。开发 down 会删除三张新增表及其事实、事件和关联数据；生产退回版本仍须按既有完整备份恢复步骤操作。

## 事实实体端点与待确认实体，结构版本 40

`000040_entity_candidates` 为事实增加可空的主体和对象实体 ID 及查询索引，新建 `entity_candidates` 与 `entity_candidate_occurrences`。候选按个人空间和规范化名字唯一，出现记录按候选、事实、端点唯一，并以外键约束候选与事实处于同一空间。删除实体只清空端点引用，删除事实会撤除其出现记录。事实合并时须在移除源事实前显式转移并去重出现记录，该行为随人工归组接口接入。

升级不删除或改写已有资料、事实文字、证据与目录，历史事实的两个新 ID 默认为 NULL，不做自动历史推断。新表与新字段均登记为 Sidecar，导入顺序保证实体在事实前、候选和事实在出现记录前。旧副本升级只补空表与 NULL 端点，非空新增数据仍严格核对。副本格式和登记版本不变。

开发 down 删除候选、全部出现记录和两列端点 ID；原资料、事实文字、出处与事件保留，但新增的审核决定、出现证据和挂接关系会丢失，不能靠再次 up 恢复。升级默认不备份，不影响迁移执行；没有本次备份时，不承诺能恢复到操作前最新状态。


## 召回缓存与归组记录，结构版本 41

`000041_recall_grouping` 新增可重建的事实向量缓存 `fact_embeddings` 与逐候选的 `grouping_decisions`。判定记录保存候选事实 ID、向量相似度、模型、初判与复核的结果及置信度、保守处理后的结果和理由。升级仅增加空表与索引，不删除或改写资料、事实、事件与证据。

开发回滚 41 到 40 删除这两张表，丢失本功能的判定审计记录与缓存；缓存可重算，审计记录不可重建。资料提及、出处及事实与事件保留。维护副本登记判定记录并按依赖顺序导入；向量缓存按当前共享模型在召回时补算。


## 人工归组保护与合并跳转，结构版本 42

`000042_manual_grouping` 为资料增加 `grouping_manual`，为事实与事件各增加 `manual_corrected` 和 `merged_into_id`。人工标记默认 false，跳转默认空字符串，禁止自身跳转。升级只增加默认字段，不删除或批量改写资料、事实、事件、出处、候选与关注。

新字段全部归 Sidecar，旧副本升级仅补精确默认值。当前副本中的非默认标记和跳转仍严格核对，副本格式与登记版本不变。开发 down 删除五个新增字段，丢失归组保护与旧 ID 的跳转能力；已经执行的移动和合并不会自动撤销，出处、提及、候选出现记录与关注保留操作后的归属。再次升级只能建立空标记，不能恢复此前的人工决定。升级默认不备份，不影响迁移执行；未做本次备份时不能承诺恢复到操作前最新状态。
