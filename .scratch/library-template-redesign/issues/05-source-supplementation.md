## Question

同一 URL 先收到摘要、后来补充全文、收到修订信息或 Web Agent 调研结果时，应怎样更新已有资料？

用少量实例决定：追加还是替换、怎样保护用户笔记、是否需要保留旧内容、摘要是否重新生成，以及重复提交相同内容如何处理。区分同一来源补充与不同来源描述同一产品，避免只因产品名称相同就合并。

本任务确认用户可见行为；URL 规范化算法和具体接口实现属于后续实施。

## Answer

### 去重与后续补充规则 V1

版本状态：按用户要求直接拟定的讨论稿，尚未改代码。用户已确认资讯、参考资料、人工笔记分库保存。以下 URL 与正文指纹规则分别应用于资讯库和参考资料库；人工笔记库单独处理。

#### 1. 如何识别已有资料

- 只在目标库内识别，不跨库合并。同 URL 在资讯库和参考资料库分别对应独立条目，不互相覆盖、去重或自动换库。
- 补充时已明确指定目标库内的条目 ID，就定位该条资料；否则有原文 URL 时在目标库内按 URL 定位。
- 无 URL、也未指定已有条目 ID，按新资料保存，允许重复。
- 不同 URL 默认分别保存；不因标题、主题、摘要或发布时间相近自动合并。
- URL 只做保守规范化，不随意删除具有资源含义的参数或改变路径含义。

#### 2. 定位后如何判断重复

- 比较本次提交内容与该条资料已保存内容的指纹。正文指纹仅用于该条资料内的确定性比较，不与全库逐篇比较。
- 内容已保存过，按重复投递返回原条目，不重复创建或附加同一份内容。
- 内容有变化，按补充或明确更新处理，不能只因 URL 已存在就跳过。
- 标题、来源日期等显式元数据修改单独处理，不因正文未变就忽略；空值不自动清空已有值。

#### 3. 同 URL：先有摘要，后来补充全文

1. 沿用原条目 ID，不新建第二份主资料。
2. 原摘要保留为摘要；新提交的全文保存为来源正文。资料同时保有精简入口与可展开阅读的全文。
3. 保存已有的用户笔记、手写摘要、星标、主题及来源信息；不由新抓取内容覆盖这些人工内容。
4. 保留首次收录时间，记录本次补充时间；补充时间不冒充原文发布时间。
5. 成功保存后更新受影响的检索索引，使全文可被检索。V1 不强制重新总结全文，摘要的进一步提炼留给独立处理操作。

全文补充由提交方明确说明，或由用户明确执行补全文操作；不凭字数更长或模型猜测就认定为全文。没有说明时仍接收为补充材料，不自动覆盖现有正文。

#### 4. 其他变化如何处理

| 新旧内容情况 | V1 行为 |
| --- | --- |
| 已有全文，后来又收到摘要或片段 | 保留全文；新增内容可作为补充，不以短内容替换全文 |
| 同 URL 收到新的片段、不同摘要，或无法判断范围的内容 | 附在同条资料中作为补充，保留本次提交信息，不自动拼接或重写现有正文 |
| 提交方或用户明确要求更新原文 | 替换该条资料的来源正文；保留上一版被替换的来源正文，作为滚动的一版历史；人工内容仍保留 |
| 原资料没有 URL，后来按条目 ID 补链接或全文 | 在原条目补充；若链接已属于同库另一条资料，保留两条并提示链接冲突，不自动合并或覆盖；其他库的相同链接不构成冲突 |
| 不同来源描述同一产品或同一事件 | 分别保存，不做语义归并 |

补充材料保留已知来源和提交时间。只有明确更新来源正文时才发生替换；普通采集与补充默认不覆盖。

#### 5. 人工笔记与 Web Agent 调研

- 人工笔记在独立的人工笔记库保存，URL 只是引用，不用它自动合并不同笔记或覆盖其他库资料。新建笔记按新条目保存；编辑已有笔记按条目 ID 明确操作，原稿保持用户提交的内容。
- Web Agent 围绕产品、选型或多个来源形成的分析报告，默认另存并引用原资料，不改写来源原文。仅重新取得同一来源全文时，才按上述补全文规则处理。

#### 6. 失败与保护

- 补充或更新失败时，原有可用内容继续保留，不提前清空正文。
- 本规则不添加链接、完整度或内容质量门槛；内容是否纳入沿用已确认的纳入标准。
- 只拟定规则，不实施版本存储、接口、索引或页面变更，不对运行数据执行操作。

#### 7. 验收示例

同库先保存 URL U 的两句话摘要，得到条目 E；之后向 U 明确提交全文，结果仍是 E，原摘要与全文均可读，人工笔记保留。再次提交相同全文不新增内容。之后再投递短摘要，全文仍然保留；只有明确更新原文操作才能替换来源正文。

若资讯库已有 U 的摘要，之后将 U 的全文投递至参考资料库，则在参考资料库新建独立条目；资讯库原摘要保留，不跨库覆盖或移动。
